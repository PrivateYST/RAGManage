## 二、视频 1：从零搭建企业级知识库

### 2.1 “10 轮提问”真正解决什么问题

企业知识库失败，通常不是模型不够强，而是项目一开始没有把以下问题说清楚：

1. **服务谁**：员工、客服、售前、研发、管理层的知识需求不同。
2. **回答什么**：制度问答、产品资料、故障排查、合同查询和经营分析不能用同一套评价标准。
3. **依据是什么**：回答必须能回溯到文档、版本、章节或业务记录。
4. **哪些内容不能回答**：权限、保密等级、时效性和高风险领域需要明确拒答或转人工。
5. **成功如何衡量**：不能只看“回答像不像”，还要看召回率、引用准确率、拒答正确率、响应时延和成本。

因此，所谓“专业提问”可以理解为一套需求澄清模板，而不是简单地让模型生成页面。建议至少覆盖：业务目标、用户角色、知识范围、数据来源、更新频率、权限模型、回答格式、引用要求、评测集和上线约束。

### 2.2 从 0 到 1 的搭建顺序

1. **建立知识范围**：先选一个高价值、低风险、边界清晰的场景，例如“售后故障排查”或“内部制度问答”。
2. **盘点数据源**：列出 PDF、Word、网页、数据库、工单、Wiki、代码仓库等来源，并标记负责人、更新时间和可信等级。
3. **清洗与切分**：去除重复页眉、目录噪声和过期版本；按标题、条款、步骤和表格语义切分，保留文档层级元数据。
4. **建立索引**：同时考虑关键词检索、向量检索和结构化过滤；企业场景通常需要混合检索和重排。
5. **设计回答协议**：要求模型给出结论、引用、适用范围和不确定性；证据不足时必须说明无法确认。
6. **接入权限**：检索前过滤用户可访问的知识，不能只在前端隐藏结果。
7. **准备评测集**：用真实问题覆盖常见问题、边界问题、过期文档、权限冲突和无答案问题。
8. **上线观测**：记录查询、召回片段、模型答案、引用、用户反馈、耗时和 token 成本，支持问题复盘。

### 2.3 对 RAGManage 的启发

- 需求创建页应先收集“业务场景、数据源、权限、更新策略、评价指标”，再允许创建知识库。
- 知识库不能只有一个“上传文件”入口，还需要文档状态、版本、解析失败原因和重新索引能力。
- 问答结果需要展示引用来源、文档版本和命中片段，方便用户判断答案是否可用。
- 管理端应把“无答案”和“低置信度答案”单独列出，作为后续补充知识或调整切分策略的依据。

## 三、视频 2：GBrain 知识库检索企业落地实战

### 3.1 企业检索和演示型检索的差异

企业检索的核心不是“能搜到”，而是“在权限、版本和业务语境下搜对”。落地时至少要处理：

- **召回完整性**：问题涉及多个章节或多个文档时，不能只返回一个相似片段。
- **结果精确性**：相似但不适用的内容会造成错误答案，需要重排、元数据过滤和时间/版本约束。
- **可解释性**：结果应显示命中文档、页码或章节、发布时间和匹配原因。
- **权限隔离**：租户、部门、角色、项目和密级都应进入检索条件。
- **时效性**：制度或产品信息更新后，旧索引不能继续成为首选证据。
- **可运营性**：解析失败、索引积压、检索耗时和模型调用失败都要有状态和告警。

### 3.2 推荐的检索链路

```text
用户问题
  -> 身份与权限解析
  -> 查询改写/意图识别
  -> 关键词检索 + 向量检索
  -> 元数据过滤（租户、部门、版本、时间、密级）
  -> 重排与去重
  -> 证据聚合
  -> 大模型生成答案与引用
  -> 置信度/拒答判断
  -> 反馈、日志与评测
```

其中最容易被忽略的是“证据聚合”和“拒答判断”。如果多个片段相互矛盾，应优先采用有效期更晚、权威级别更高的版本，并将冲突显式告诉用户；如果没有足够证据，应返回需要补充的信息或转人工，而不是强行生成答案。

### 3.3 企业落地的评测指标

| 层级 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Recall@K、命中率、MRR/nDCG | 正确证据是否进入候选集，以及排序是否靠前。 |
| 生成 | 忠实度、引用准确率、答案完整性 | 答案是否被证据支持，引用是否真正支撑结论。 |
| 安全 | 越权命中率、敏感信息泄露率、拒答准确率 | 无权限内容是否可能被召回或间接泄露。 |
| 体验 | P50/P95 延迟、失败率、首 token 时间 | 用户等待时间和服务稳定性。 |
| 经营 | 单次问答成本、人工转交率、问题解决率 | 是否产生真实业务价值。 |

## 四、视频 3：RAG、LLM Wiki、Ontology 本体如何选

视频公开文案给出的判断非常关键：三者不是互相替代的产品类别，而是解决不同层次的问题。

### 4.1 RAG：检索资料，回答时找依据

RAG（Retrieval-Augmented Generation）把外部资料检索出来，再交给大模型生成答案。它适合：

- 文档问答、制度查询、产品手册和 FAQ；
- 资料变化较快、希望不频繁训练模型的场景；
- 需要回答时给出原文引用的场景。

它的边界是：RAG 擅长“从资料中找答案”，不天然等于业务知识图谱，也不能自动解决实体统一、跨系统关系和复杂规则推理。

### 4.2 LLM Wiki：提前整理和沉淀知识词条

LLM Wiki 可以理解为面向人和模型共同维护的结构化知识词条层。视频文案强调它用于解决“文档散乱、版本冲突”。典型词条包括：

- 产品、客户、部门、术语和故障码的标准定义；
- 同义词、别名、旧称和禁止使用的称呼；
- 版本变更、适用范围、负责人和关联文档；
- 经审核的问答、流程和经验结论。

它适合把分散文档中反复出现的稳定事实提炼出来，降低每次都从长文档重新寻找定义的成本。Wiki 内容需要负责人、审核状态和变更记录，否则会成为另一套失真的资料库。

### 4.3 Ontology 本体：定义业务实体、关系和规则

Ontology 关注“业务世界由什么对象组成，它们如何关联”。视频文案强调它用于“打通多系统业务数据，让规则匹配真实业务对象”。典型建模内容包括：

- 实体：客户、合同、产品、订单、设备、工单、组织；
- 属性：状态、时间、归属、等级、有效期；
- 关系：客户签署合同、合同包含产品、设备产生工单；
- 约束：状态转换、归属关系、唯一性和权限边界。

它适合跨系统查询、复杂关联分析、规则判断和需要实体一致性的场景。Ontology 建设成本高于普通文档检索，应该从高价值实体和关键关系开始，而不是一次性建完整世界模型。

### 4.4 三者组合方式

```text
Ontology：确定“问的是哪个真实业务对象，以及对象之间如何关联”
LLM Wiki：提供“标准定义、术语、规则和已审核知识”
RAG：从原始文档和实时资料中“找出证据并生成带引用的回答”
```

一个“查询客户合同风险”的请求，可能先由 Ontology 找到客户、合同和产品关系，再从 LLM Wiki 获取术语和规则，最后用 RAG 检索合同正文、制度和最新变更记录，组合出可追溯的结果。

## 五、选型决策表

| 业务情况 | 首选能力 | 是否需要补充 |
| --- | --- | --- |
| 文档数量少、问题主要是查资料 | RAG | 做好切分、引用和权限即可。 |
| 文档多、术语混乱、版本冲突频繁 | RAG + LLM Wiki | 先治理术语、版本和负责人。 |
| 跨系统按客户/合同/设备关联查询 | RAG + Ontology | 先统一实体 ID 和关系定义。 |
| 规则判断依赖真实业务对象 | Ontology + 规则层 + RAG | RAG 提供证据，规则层负责确定性判断。 |
| 高风险制度、合规和审计场景 | 三者组合 | 必须有权限、版本、引用、审批和审计日志。 |

快速判断可以归纳为：

- **简单文档问答：RAG 足够。**
- **文档多且需要沉淀标准知识：加入 LLM Wiki。**
- **需要理解实体关系并打通多系统：加入 Ontology。**

## 六、面向 RAGManage 的分阶段实施计划

### 阶段 1：可用的文档 RAG

选择一个场景，完成文档上传、解析、切分、索引、混合检索、引用回答、权限过滤和基础评测。此阶段的目标是证明“真实问题能得到可核验答案”。

### 阶段 2：知识治理与 LLM Wiki

增加术语词条、同义词、版本、负责人、审核流程和文档关联。对高频实体和高频问法进行人工确认，把稳定事实从长文档中提炼出来。

### 阶段 3：Ontology 和业务系统连接

从一个核心业务域开始定义实体、关系和唯一标识，接入 CRM、ERP、工单或资产系统。让检索先定位真实对象，再联合文档证据回答。

### 阶段 4：评测、运营和治理

建立离线评测集、在线反馈闭环、数据血缘、审计日志、成本监控和版本回滚机制。任何模型、切分、重排或提示词调整，都应能比较变更前后的效果。

## 七、落地检查清单

- [ ] 是否明确了首个业务场景和不做的范围？
- [ ] 每个数据源是否有负责人、可信等级、版本和更新时间？
- [ ] 文档解析失败、重复文档和过期文档是否可见？
- [ ] 检索是否支持关键词、向量、元数据过滤和重排？
- [ ] 权限是否在检索层执行，而不是只在前端隐藏？
- [ ] 答案是否展示可点击的来源、版本和命中片段？
- [ ] 无答案、证据冲突和低置信度是否有明确处理？
- [ ] 是否准备了真实问题评测集和人工标注标准？
- [ ] 是否记录延迟、失败、成本、反馈和人工转交？
- [ ] 是否为术语、实体、关系和规则指定维护责任人？

## 八、结论

这三个视频可以串成一条企业知识库建设路线：先用专业提问把目标、数据和边界问清楚；再把 RAG 检索链路做成可评测、可引用、可运营的企业服务；当文档治理和跨系统业务理解成为瓶颈时，再分别引入 LLM Wiki 和 Ontology。本质上不是在三个名词中“选一个”，而是按业务复杂度逐层增加能力。
