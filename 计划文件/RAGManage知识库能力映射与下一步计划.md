# RAGManage 知识库能力映射与下一步计划

> 基于《抖音知识库视频整理与企业落地要点》以及当前仓库实现状态整理。
>
> 分析时间：2026-10-15

## 一、结论先行

RAGManage 已经具备企业文档 RAG 的主链路，不需要重新搭建一个知识库原型：

```text
上传文档 -> 异步解析 -> 文档版本 -> 切片/嵌入 -> 构建 -> Release 发布
        -> 权限过滤 -> 混合检索 -> 证据组装 -> 引用问答 -> 反馈/审计
```

当前最适合结合视频内容的方向是：

1. **先完成 RAG 质量闭环**：建立真实问题集，达到或解释 Recall@10、引用支持性、无答案处理等指标。
2. **在现有知识库之上增加 LLM Wiki MVP**：做术语、实体别名、版本和负责人治理，不另起一套问答系统。
3. **暂缓完整 Ontology 落库**：先通过概念模型和实体解析接口验证一个真实跨系统场景，再决定图模型或关系模型。
4. **把知识库创建从“建容器”升级为“建业务场景”**：增加目标、范围、数据源、权限和评价标准，让视频中的“专业提问”真正进入产品。

## 二、当前项目已经能做什么

| 视频中的能力 | 当前项目状态 | 代码/功能依据 | 判断 |
| --- | --- | --- | --- |
| 文档 RAG | 已具备主链路 | `backend/app/rag/parsing.py`、`retrieval.py`、构建与发布模块 | 可直接用于首个业务试点。 |
| 混合检索 | 已具备 | pgvector 向量召回、中文关键词召回、RRF 融合、证据去重 | 可以开始做真实问题集和参数评测。 |
| 引用回答 | 已具备 | `backend/app/rag/chat.py`、引用校验、来源权限重校验 | 已符合“回答必须有依据”的产品方向。 |
| 文档版本和时效 | 已具备基础 | 文档版本、构建快照、Release、回退、版本对比 | 可支撑版本优先和可审计回答。 |
| 权限隔离 | 已具备核心能力 | 空间/知识库成员、Release 来源过滤、跨空间测试 | 可作为企业化的安全底座。 |
| 重新解析/重新嵌入 | 已具备 | 文档详情入口、任务重排、审计链路 | 可支撑知识持续更新。 |
| 运行配置 | 已具备 | Ingestion、Embedding、Runtime Profile，不可变快照 | 可做检索策略和回答规则实验。 |
| 检索诊断 | 已具备基础 | `/api/v1/search-test`、Trace、候选排名与耗时 | 能定位召回问题，但样本和指标还不完整。 |
| 评测 | 有脚本，未完成闭环 | `backend/scripts/evaluate_recall.py`、`docs/evidence-recall-evaluation.md` | 目前最大短板。 |
| LLM Wiki | 尚未实现 | 没有词条、别名、审核、变更历史实体 | 可在现有文档/知识库模型上增量实现。 |
| Ontology | 尚未实现 | 没有实体、关系、跨系统 ID 和规则层 | 暂不适合直接做完整功能。 |

## 三、可以直接结合到项目的能力

### 3.1 把“10 轮专业提问”变成知识库创建向导

现有创建知识库流程可以增加一组结构化字段或分步向导，避免用户只填写名称后直接上传文件。建议收集：

- 业务目标和首个使用场景；
- 服务角色和允许访问的空间/成员；
- 知识范围与明确不包含的范围；
- 数据源、负责人、可信等级和更新频率；
- 期望回答格式、引用要求和拒答规则；
- 评测问题数量、目标 Recall@K、时延和成本约束；
- 是否需要术语治理或后续接入业务实体。

第一版不需要接大模型自动生成整套方案。使用结构化表单保存结果，并根据结果生成 Ingestion/Runtime Profile 默认值即可，稳定性和可追溯性更好。

### 3.2 把企业检索链路做成可解释的检索策略

当前检索已有向量、关键词、RRF、Release 和权限过滤。下一步可补齐：

- 检索过滤条件的可视化：版本、更新时间、文档类型、密级或业务标签；
- 每条候选的召回来源：向量排名、关键词排名、融合分数、过滤原因；
- 版本冲突提示：同一主题存在多个有效版本时，展示采用版本及原因；
- 证据集合状态：证据不足、证据冲突、来源失效、索引未就绪；
- 可选的重排器接口，先保留 Runtime Profile 配置，不立即绑定某个模型。

这些能力大部分可以复用现有 Trace、候选结果、Release 和 Citation 数据，不需要重做数据库主链路。

### 3.3 把 LLM Wiki 做成“受审核的知识治理层”

LLM Wiki 最适合先解决当前文档 RAG 的两个实际问题：术语不一致和版本冲突。建议 MVP 只做以下对象：

| 对象 | 最小字段 | 用途 |
| --- | --- | --- |
| 词条 | 名称、定义、类型、状态、负责人 | 给人和模型提供稳定定义。 |
| 别名 | 词条 ID、别名、来源、是否标准 | 支持同义词和旧称召回。 |
| 版本 | 生效时间、失效时间、适用范围、变更说明 | 处理时效和冲突。 |
| 关联文档 | 词条 ID、文档版本/切片、关系类型 | 让词条结论能回溯原文。 |
| 审核记录 | 提交人、审核人、审核状态、时间 | 防止未经确认的事实进入回答。 |

推荐接入方式：

1. 检索前用词条别名扩展查询或做实体标准化；
2. 检索后将已审核词条作为高可信证据，与原文片段一起组装；
3. 词条必须保留来源引用，不能成为无来源的“第二个真相库”；
4. 词条变更进入现有审计日志，并在需要时触发重新评测，而不是自动重建全部索引。

第一版可以采用 PostgreSQL 关系表，不需要引入图数据库。只有当关系查询成为主要业务需求时，才评估 Ontology 专用存储。

### 3.4 为 Ontology 先做轻量接口预留

Ontology 目前不应直接作为下一次迭代的大功能。可以先做三个无数据库依赖的边界：

- `entity_type`：实体类型，如客户、合同、产品、设备、工单；
- `entity_id`：外部系统稳定标识；
- `relation_hint`：问题中识别出的关系或筛选条件。

将它们作为检索请求的可选上下文，暂时映射到文档元数据过滤和词条关联。等拿到真实的“按客户查合同/按设备查故障”问题集，再决定是否建设实体关系表、同步任务和规则执行层。

## 四、目前不建议马上做的事项

- **不要先做完整知识图谱**：没有明确业务实体、唯一 ID 和高频关系时，建模成本会高于收益。
- **不要先做自动词条抽取全自动发布**：抽取结果必须经过审核，否则会把模型猜测写成企业事实。
- **不要只通过增大 top_k 解决召回问题**：先确认切分、元数据、版本过滤和评测标注是否正确。
- **不要把普通对话和知识问答混为一个指标**：项目已有 assistant scope 路由，企业事实问题应单独统计。
- **不要把视频中的产品名当成当前技术选型**：GBrain 只作为检索落地案例参考，不能替代对现有栈的实测。

## 五、下一步工作顺序

### P0：完成 RAG 质量基线

这是下一步最应该做的工作，直接对应当前计划中的未完成项：

1. 建立医院资料问题集，再补充技术、产品和故障排查问题集；
2. 将样本拆成训练集、调试集和留出集，避免用调参问题评估自己；
3. 为每个问题标注可接受文档、可接受片段、是否应拒答和权限前提；
4. 运行 Recall@5/10、引用支持性、无答案正确率和延迟评测；
5. 对未命中样本回查切分、元数据、版本、关键词抽取和向量模型；
6. 把结果写入 `计划文件/RAGManage全量业务实施计划.md`，形成差距分析，而不是只报告一个百分比。

验收目标建议沿用现有计划：Recall@10 达到 90%，答案可用率达到 85%，引用支持性达到 95%，无答案正确处理达到 90%。如果暂时达不到，必须保留按问题类型拆分的差距报告。

### P1：补齐知识库场景和数据治理元数据

在 P0 有数据后，再改知识库创建和文档管理：

- 知识库增加业务场景、目标用户、范围、负责人和更新策略；
- 文档增加可信等级、来源系统、有效期、业务标签和责任人；
- 检索过滤支持这些元数据，并在引用侧栏展示；
- 过期/冲突文档进入治理列表，不能只依赖用户发现问题后反馈。

这一步优先利用已有文档、版本、Release、成员和审计模型，控制迁移范围。

### P2：实现 LLM Wiki MVP

建议以一个词条域启动，例如“产品术语 + 常见别名 + FAQ 标准答案”：

1. 新增词条、别名、来源关联和审核状态；
2. 提供管理页和只读详情页；
3. 查询改写时使用已审核别名；
4. 回答时把已审核词条作为带来源证据；
5. 增加词条变更审计和针对性回归问题。

这一步完成后，才能判断 LLM Wiki 是否实际改善了 Recall、引用支持性和用户反馈。

### P3：Ontology 概念验证与试点

只有出现明确业务需求时再做：

- 选择一个业务域和 3 至 5 种实体；
- 明确外部系统唯一 ID、同步频率和权限继承；
- 用 20 至 50 条跨实体问题验证实体解析和关系过滤；
- 评估关系表、图数据库或外部业务系统查询的成本；
- 通过后再设计正式同步、规则和审计能力。

### P4：试点上线和性能闭环

继续执行现有全量实施计划中尚未完成的性能、安全和恢复验收：

- 管理 API P95、检索/重排 P95、首字 P95；
- 并发 1/5/10 及构建与问答并行压力；
- 会话、撤权、跨空间、模型变更和 Worker 重放回归；
- 数据库、原文件、Profile 和 Release 恢复演练；
- 3 至 5 名内部用户、至少 5 个工作日的真实试点。

## 六、建议的第一个具体迭代

建议下一个迭代只包含一个目标：**让 RAGManage 能用真实问题证明当前 RAG 是否可靠**。

### 后端/评测

- 扩展评测 JSONL 契约：加入 `expected_chunks`、`should_refuse`、`permission_scope` 和问题类型；
- 输出 Recall@K、引用支持性、拒答准确率、按类型分组的 miss 列表；
- 将 Trace 中已有的向量排名、关键词排名、融合分数和耗时纳入评测报告；
- 为版本冲突、无答案和越权候选增加回归测试。

### 前端

- 在检索调试页增加“问题类型/评测集/版本过滤”筛选；
- 展示候选被过滤的原因和当前 Release 版本；
- 在问答引用侧栏展示文档版本、有效期、可信等级和词条关联（字段准备好后启用）；
- 增加“答案有帮助/证据不支持/应拒答”反馈分类。

### 数据准备

- 先使用现有医院 Markdown 作为基线；
- 再加入一组技术或产品资料，避免只对单一文档风格优化；
- 每类至少准备常见问题、跨文档问题、无答案问题、过期版本问题和权限问题。

## 七、最终判断

RAGManage 当前已经可以承接视频中“企业级 RAG 检索落地”的大部分核心能力，优先价值不在于再堆一个新名词，而在于把已有链路用真实数据评测、解释和运营起来。LLM Wiki 是最自然的下一层能力，因为它能直接改善术语、别名和版本治理；Ontology 属于后续业务建模能力，应由真实跨系统问题驱动。下一步先做 P0 评测基线，然后把评测结果反向驱动知识库场景字段、元数据治理和 LLM Wiki MVP。
