# RAGManage 最终可行方案

版本：1.0｜日期：2026-09-17｜用途：开发实施基线与逐步执行计划。

## 结论

建设一个面向内部团队的知识库管理与 RAG 问答系统。采用 **Vue 3 + TypeScript + shadcn-vue、FastAPI、PostgreSQL + pgvector、Celery + Redis、独立模型服务**，以模块化单体交付。

先支持电子文档，再接入受控的结构化记录。核心不是堆齐组件，而是完成内容管理、正确检索、证据引用、权限、更新发布、失败恢复与评测的可靠闭环。

这份方案已形成可执行设计；硬件容量、模型兼容性、性能与业务效果仍须按计划实测。“最终”表示本轮方案汇总，不表示软件已实现或全部假设已经用户确认。

## 如何执行

1. 按 PLAN 的依赖顺序推进；每完成一步，填写结果与证据位置后再勾选。
2. P01–P08 先确认数据和模型路线成立；P09–P23 完成内部试点；P24–P27 完成生产准备；P28–P30 为结构化记录增量。
3. P28–P30 默认作为 V1.1；如果结构化记录是首批核心资料，在 P01 将其提升为 V1.0 上线前置，并重新估算排期。
4. 不执行旧文档中的 7 卡 TP、任意维度 HNSW、异构嵌入模型混写等示例。这里是独立实施基线，原文档作为历史材料保留。

## 默认边界

- 单组织内部使用，多知识库、多成员；底层带 tenant，测试两个租户隔离。暂不开放租户自助注册。
- 权限到知识库；跨知识库问答、文档级 ACL、扫描 OCR、复杂表格、自动连接器后置。
- 单知识库会话，文档需发布才参与问答；新版本处理失败时继续使用旧发布版本。
- 未授权使用外部模型服务时采用本地服务，不自动将资料发往外部。
- 当前机器/团队/模型未实地核验，采用 P01/P03 的盘点结果替代旧文档假设。
- 本次交付仅包含规划文档；全部开发步骤初始为未完成，工期与性能都是计划值。

## 变更规则

业务范围改变时先更新 01 与 PLAN；数据/版本契约改变时同步更新 02、03 与 06。新增模型必须通过兼容性与效果评测；不得只改模型名并继续使用旧向量。
