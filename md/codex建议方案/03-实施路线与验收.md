# 实施路线与验收

本路线以小团队内部试点为假设，用阶段退出条件驱动；不把原文的“3–4 个月”当已确认承诺。

## 1. 阶段计划

| 阶段 | 主要交付 | 退出条件 | 参考投入 |
|---|---|---|---|
| S0 场景与资料盘点 | 一个使用场景、代表性文档、真实问题、硬件/模型清单 | 明确谁用、问什么、什么算答对 | 2–3 人日 |
| S1 最小证据链 | 解析→切片→嵌入→检索→引用回答，评测脚本 | 可定位错在解析/检索/生成；确认至少一条可行链路 | 5–8 人日 |
| S2 内部管理闭环 | 登录、知识库、上传、任务、预览、问答、基本权限 | 非技术用户完成上传到引用核对；隔离测试通过 | 10–15 人日 |
| S3 更新和发布可靠性 | 内容版本、构建、发布、失败恢复、删除、回退 | 故障重试不重复，旧内容不复活，新旧索引不混用 | 8–12 人日 |
| S4 检索优化与试点 | 向量/词法/重排对比、留出集、代表规模压测 | 达到商定质量与延迟门槛，完成试点反馈闭环 | 5–10 人日 |
| S5 上线准备 | 环境隔离、备份恢复、监控、运维说明 | 恢复演练和权限回归通过，资源基线明确 | 4–7 人日 |

约 34–55 工程人日只是第一期试点范围的初步工作量预算，尚未包含大规模连接器、复杂 OCR/表格和长时间用户试点。AI 辅助并不消除集成、验收与现场部署成本；S1 后重估。各阶段都有测试，不能把权限或数据一致性留到最后才检查。

S1 可用固定配置和简化脚本，需明确其临时 schema；S2 开始建立正式领域表、不可变内容与 profile 标识；S3 完成发布协议。避免先写可变数据模型，再在最后补不可变版本。

结构化记录若确认第一期必需，新增字段映射、增量 upsert、源端删除标记、同步水位、记录引用和数值问题路由；独立估算工期，不挤入“顺便支持”。

## 2. 首轮评测集

先准备 20–50 份能代表实际难度的资料，不全用结构理想的 Markdown；若实际以 PDF 为主，S1 就必须包含 PDF。

建立 50–100 条初始真实问题，预算不足时先用 20 条探路，但不能据此宣称生产可用。建议包含：

- 直接事实问题、同义表达、精确编号/型号。
- 跨段落组合、多文档冲突、追问。
- 资料中没有答案的问题。
- 已更新/已停用内容、权限不可见内容。
- 解析困难、表格中才有答案的例子；不支持时应明确拒答或标记限制。

每题保存：问题、适用知识库与身份、参考证据版本/位置、答案要点或无答案标签、可接受表达、评分规则。按调参集与独立留出集分开；不能在同一批题上反复调参后把提升当泛化能力。

## 3. 指标与建议门槛

以下为内部试点候选门槛，需业务方确认，不是测得成绩。按类别报告分子/分母，避免小样本百分比掩盖问题。

| 指标 | 定义 | 试点候选门槛 |
|---|---|---|
| Evidence Recall@10 | 有答案问题中，前十候选覆盖标注证据的比例；多证据题分别统计完整覆盖 | ≥ 90% |
| 答案可用率 | 人工按答案要点评分，正确且没有关键无依据结论 | ≥ 85% |
| 引用支持性 | 抽样检查引用是否真实支持对应论断 | ≥ 95% |
| 无答案处理正确率 | 无答案题明确拒答/澄清且没有编造事实 | ≥ 90% |
| 越权暴露 | 两租户、多成员角色及撤权回归中的内容泄露 | 测试集内为 0；不等于形式化安全证明 |
| 删除与更新 | 提交后新请求不能检索删除内容；更新按发布规则生效 | 全部设计用例通过 |
| 索引发布可靠性 | 构建不完整不能发布；回退不混模型空间 | 全部设计用例通过 |

同时测解析有效率、空文档率、失败原因、每千页处理耗时、嵌入吞吐和存储增长。先知道资料是否被正确读入，再解释问答成绩。

不将“必须证明多路召回更好”作为强制结论。保持同一资料/问题/生成模型/预算，比较：向量、词法、向量+词法、融合+重排。若复杂方案收益不足就保留简单方案，记录实际代价。

## 4. 性能测试口径

每条结果必须附：硬件、模型 revision/量化、服务版本、输入/输出 token、文档及 chunk 数、过滤选择性、并发、缓存冷热状态。

- 分别报告 P50/P95 首字时间、完整回答时间、tokens/s、排队与错误率。
- 先测 1、5、10 并发，再根据实际业务扩展。单请求快不代表并发容量达标。
- PDF 解析按页数和版面类型分类，不用“100 页”代表所有文件。
- ANN 对比精确检索的 Recall@k，记录过滤后不足 k 的频率与 SQL 执行计划。
- 重建与问答同时运行，验证后台任务不会挤占所有在线容量。
- 在实机确认模型与并发前，不承诺 8 秒首字或 50 并发。性能 SLA 应在 S1 基线和业务容忍度明确后确定。

## 5. 必测故障与一致性场景

| 场景 | 预期行为 |
|---|---|
| worker 中途退出、Celery 重复投递 | 已完成项不重复，未完成项可恢复 |
| API 写任务后消息派发失败 | outbox/对账补发，任务不永久挂起 |
| 模型超时/显存不足/输出维度错误 | 明确失败或受控重试，不写错误向量 |
| 构建期间更新/删除源文档 | 发布前发现代次变化，补齐或拒绝发布 |
| 只修改 top-k 或提示词 | 新 runtime 生效，不重嵌入、不查询空索引 |
| 0.6B 升级 4B，包括维度相同情况 | 查询与文档编码保持一致，无跨空间混查 |
| 上传新版本失败 | 旧有效版本保留，错误可见 |
| 删除后回退旧 release | 不恢复已删除内容的可访问性 |
| 撤销权限后查看历史引用/调试/下载 | 各入口执行相同授权策略 |
| 流式生成过程中断 | 留下未完成/失败状态，不误标成功 |
| PostgreSQL 恢复但原文件未恢复 | 恢复检查失败，不声称恢复成功 |
| API 与 worker 运行在不同容器 | 使用共享卷或对象存储访问同一文件 |

## 6. 上线前的最低运维闭环

监控：队列长度、任务失败、模型可用性、显存峰值、问答延迟、数据库容量和追踪增长。

追踪默认保留必要的候选 ID、版本、排名与耗时；完整候选正文只在授权调试/故障分析时按受控期限保存。消息引用与调试追踪分开保留，清理追踪不会让用户历史引用全部消失。具体保留天数由数据政策与容量预算决定。

首期追踪表可不分区，采用索引与分批清理。确需时间分区时一起设计分区键、唯一键、外键与引用生命周期。

恢复演练需重新拉起 PostgreSQL、原始文件存储和 profile/model 配置，验证一份真实文档可打开、一条引用可定位、一条问答可复现其检索版本。RPO/RTO 在部署前与业务确认。

## 7. 待业务确认，不应被技术文档代替的决策

以下为后续讨论清单，不要求一次回答所有问题。

1. 第一批用户与场景：技术资料、企业制度、客服、项目档案中的哪一个最重要？
2. 核心输入：电子文档、扫描件、表格、数据库记录分别占多少？
3. 权限范围：知识库级是否足够？是否需要第一期就服务多个独立组织？
4. 生成模型准确名称、可用算力、已有服务 endpoint 和数据出域限制。
5. 用户数量、同时请求规模、更新频率、删除/历史保留要求。
6. 团队投入、上线时间及质量门槛；这些共同决定是否纳入结构化数据与复杂 PDF。

我的建议起点：**一个内部团队、一个明确场景、多知识库、电子文档优先，先完成带引用的可靠闭环。** 若这与既有真实业务要求不同，应调整范围，而不是为了遵守任何一份旧定案牺牲需求。
