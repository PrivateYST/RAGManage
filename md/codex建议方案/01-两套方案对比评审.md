# 两套方案对比评审

## 1. 推荐结果与适用条件

**DeepSeek 更适合充当架构基线，但两套文档都还没有达到可原样执行的实施定案水平。**

这个判断以“小团队、先做内部知识库、真实规模与生产算力尚未验证”为前提。如果已有成熟 MySQL/Milvus 运维平台，或明确需要大型独立检索集群，选型需结合既有环境重估，不能仅凭文档宣布 pgvector 胜出。

| 维度 | Claude | DeepSeek | 结论 |
|---|---|---|---|
| 产品与管理功能 | 上传、会话、权限、运维清单较完整 | 补充知识库配置、切片预览、检索调试 | 合并有价值的能力，缩减第一期范围 |
| 领域模型 | 用户直接拥有文档，没有明确知识库表 | 租户→知识库→数据集→内容 | DeepSeek 更合理 |
| 服务数量 | MySQL、Milvus、MinIO、Redis 等 | PostgreSQL + pgvector 收敛存储 | 小团队优先后者，原文件仍要存储和备份 |
| 检索质量 | 固定切片起步，后续有混合检索和重排 | 结构感知、多来源召回、重排和追踪 | DeepSeek 更系统，但多来源不等于混合检索 |
| 变更维护 | 缺少索引版本和发布机制 | 配置版本、重嵌入、回滚 | 后者方向好，需分离运行配置与索引构建 |
| 研发顺序 | 先基础设施与业务页面，较晚系统性评测 | 前置最小链路验证 | 后者更好；评测脚本应持续保留 |
| 部署准确性 | 7 卡 TP 命令有问题 | Windows 推理路径和显存承诺不严谨 | 两者都需实机验证 |
| 上线可信度 | 指标多为未经测试的目标 | 指标仍主要是估计 | 都不能当作性能承诺 |

## 2. Claude 值得保留的部分

- 管理闭环比较直观：文档上传、异步处理、状态、会话、引用、日志和备份。
- FastAPI、Vue、shadcn-vue、Celery 的职责划分可继续使用。
- MySQL + Milvus 本身不是错误：有独立检索负载和成熟运维时是合理选项；问题在于当前材料未证明必须引入这些成本。
- 不能采信 DeepSeek 所说的“Claude 未提及重排”。Claude《开发计划与实施路线图》239–240 行已有混合检索和 Rerank，273–277 行再次列出 BM25 和重排。正确批评是：评测前置不足、细节不够，而不是完全没考虑。

## 3. Claude 的主要问题

### C1：知识库管理系统缺少知识库实体

依据：《数据库表结构设计》§2、§3、§5；《系统架构设计》201 行起。

文档、会话主要归属 user，每用户一个 Milvus Collection。上传者、租户和知识库被混在一起，团队共享与按知识库管理模型/权限难以自然落地。应显式建立 tenant、knowledge_base、membership，再决定向量物理隔离策略。

### C2：Qwen2.5-7B 的 7 卡张量并行不可照搬

依据：《系统架构设计》404 行、《技术选型清单》185 行：`--tensor-parallel-size 7`。

官方 Qwen2.5-7B-Instruct 配置为 28 个 attention heads、4 个 KV heads。已核对的 vLLM Qwen2 实现要求 KV heads 按 TP 整除或被 TP 整数倍复制。TP=7 不满足 7 % 4 == 0；不能因为 28 可被 7 整除就认为命令合法。

应先单卡验证 7B 的真实显存与吞吐，再按并发选择副本或受支持的并行度。没有证据需要七卡协同承载一个 7B 实例。

### C3：性能指标口径不闭合

依据：《技术选型清单》418–419 行。

20–30 tokens/s 与“5 秒生成完整答案”不能同时适用于任意长度。500 token 答案仅生成就约 17–25 秒。应分别定义排队时间、首字时间、生成速度、完整输出时间与输出长度。

### C4：数据库示例不能直接作为迁移执行

依据：《数据库表结构设计》§7.1、338 行。

`documents` 索引引用了未定义的 `status` 字段。按 created_at 分区还需解决 MySQL 分区键与唯一键要求，以及所选存储引擎的外键限制。示意设计不等于已验证 DDL。

### C5：跨库一致性与版本发布缺少协议

MySQL 写入、对象上传和 Milvus 向量更新不是一个事务。文档删除、任务失败、模型升级期间，需定义幂等、补偿、有效版本和旧数据清理。仅列出异步队列不能保证内容一致。

## 4. DeepSeek 的关键修正

### D1：2560 维与 vector HNSW 的限制冲突

依据：《技术选型清单 v2.0》232 行，数据库设计 §5.3、§11。

方案把生产 4B 嵌入输出设为 2560 维，同时采用 `vector_cosine_ops` HNSW。pgvector 官方说明：该类 `vector` 索引最多 2000 维，`halfvec` 索引最多 4000 维。无维度 `vector` 列能存储，不代表可直接建立任意维度的 ANN 索引。

可选修正：在模型与服务支持、评测通过时使用 1024/1536 等输出维度；或使用 `halfvec(2560)` 索引并评估精度损失。不能简单把示例中的 1024 改成 2560。

### D2：索引表达式和查询不匹配

依据：《数据库表结构设计 v2.0》393–413 行。

索引表达式为 `embedding::vector(1024)`，查询却使用 `embedding <=> $1::vector`。应使查询与表达式索引匹配，并通过 `EXPLAIN (ANALYZE, BUFFERS)` 验证；按配置版本创建部分索引时，还需验证参数化查询及 generic plan 是否能证明部分索引谓词。

### D3：“同一 SQL 过滤”不等于 ANN 先过滤再召回

依据：《系统架构设计 v2.0》§2、§8。

同库有事务和 SQL 表达上的便利，但 pgvector 近似索引通常扫描候选后再应用过滤，严格过滤可能导致结果少于 top-k。官方建议提高搜索宽度、使用 0.8.0 起的 iterative scan，并按数据分布考虑部分索引、分区或小集合精确检索。

Milvus 也支持标量过滤。选型理由应是运维成本、事务需求和实测结果，不能写成“只有 pgvector 能过滤”。

### D4：总配置版本同时承担索引和问答版本，语义不清

依据：《系统架构设计 v2.0》§3.2；数据库设计 `kb_configs`、`config_versions`、`chunks`。

提示词、temperature、top-k、reranker 等通常不改变已有文档向量；解析器、切片、嵌入模型变化才影响索引产物。当前以同一配置版本绑定向量并作为查询过滤，若只改 top-k 后激活新版本，新版本下可能没有向量；为了避免空结果而复制或重算全库又浪费资源。

应分别建运行配置版本与索引构建版本，发布时关联两者，并保存一次问答真正使用的版本组合。

### D5：0.6B 批处理不能填充 4B 的在线索引

依据：《技术选型清单 v2.0》§5.1、318 行。

文中既说生产用 4B，又分配 0.6B 专供批量重嵌入，容易被实现为异构模型混写。不同模型即使维度相同也不代表向量空间兼容。离线导入与在线查询必须使用同一 embedding profile；0.6B 只应用于独立试验索引。4B 索引的批处理应使用相同 4B 模型及编码规则的独立服务副本。

### D6：开发部署与显存规划需要重新表述

依据：《项目定案》§3、§6；《技术选型清单 v2.0》§5.4、489 行。

前文指出 Windows 不支持 vLLM，后文又统称 GPU 服务在 Windows 宿主机直接运行。应区分 Windows 原生 Ollama 与 WSL2/Linux 下的 vLLM/TEI，分别验证模型、驱动和协议支持。

27.3B 量化权重估算不包含全部 KV cache、运行时缓冲、长上下文和并发开销。“4B 在开发阶段跑不了”过于绝对：单独加载或分时运行可能可行；“三种模型可以常驻 24GB”也尚无实测依据。

### D7：多来源召回不是完整的混合检索方案

文档路和记录路都是向量召回，不能代替关键词对编号、型号、条款的匹配。按来源使用 RRF 还需谨慎：两个候选集合互不重叠时，得分主要取决于各路名次和权重，不能获得同一候选被多种检索器共同支持的收益。

建议先比较向量基线与“向量 + 中文词法检索”，再按业务数据增加来源路由。RRF 本来就通过排名缓解原始分数不可比的问题；重排值得实验，不是多路召回在数学上的必需条件。

### D8：权限和缓存缺少闭环

依据：《技术选型清单 v2.0》211 行；架构设计 §3.1、§8。

tenant_id 只隔离租户，不代表用户有知识库访问权。查询、下载、引用、历史消息、召回调试页都应验证当前权限。缓存只含 tenant/kb/config/query 时，未覆盖数据集过滤、内容更新和权限变化，可能返回过期或越权内容。

第一版建议不缓存问答结果。必要时缓存键至少覆盖主体授权范围、过滤条件、内容代次、索引版本、运行版本和问题；命中后仍进行当前授权检查。

### D9：表结构和运维描述尚未闭合

- 追踪明细表没有 created_at，却要求按该字段分区；后面的分区示例建的是追踪头。应补明细时间列，或先采用关联头表时间的分批清理。
- PostgreSQL 分区表的唯一约束需包含分区键；设计 PK/FK 时要一起处理，不能将 `id` 单列主键原样迁移到时间分区表。
- `chunks` 保留策略提到软删除，但字段中没有 deleted_at，也未完整定义由源文档状态屏蔽旧块的查询。
- 不同 database 属于逻辑隔离，不是物理隔离。建议开发和生产独立实例、凭据、卷与备份目标。
- 采用本地文件存储时，Compose 示例未给 API 与 worker 共享文件卷；跨容器解析不能依赖 API 的容器内部路径。
- “只建四张表”的阶段零与正式外键依赖不兼容：正式 `chunks` 还引用文档/记录等表。验证脚本应使用明确的简化 schema，或按依赖建立最小闭合表集。

### D10：技术判断与需求确认不宜绝对化

python-docx 能读取段落和样式，pdfplumber 能提供字符位置与表格提取能力；“二者只能提取纯文本”不准确。LangChain 也有结构相关切分器，是否采用要看质量和维护成本。

“27.3B 不如小模型遵循拒答”“硬盘绝不是瓶颈”“十万/千万是数据库选型分界”都缺乏当前项目实测支持。十万 chunks 与十万份文档也不能互换；原文各处规模假设不一致。

## 5. 推荐取舍

采用：PostgreSQL + pgvector、显式知识库模型、结构优先切片、异步任务、版本化构建、引用定位、检索追踪、先评测再扩展。

修正：将配置拆分、固定首个嵌入配置、明确 ANN 索引策略、统一模型空间、落实成员权限和删除失效、细化任务幂等与发布。

后置：全部参数可视化、三种融合模式、多个模型同时常驻、全量连接器、SaaS 开通计费、提前分配十张 GPU。

不能后置：内容有效性、基本权限、失败可见、引用溯源、最小评测集和备份恢复。
