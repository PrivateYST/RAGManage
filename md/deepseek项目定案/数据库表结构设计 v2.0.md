# RAG 知识库系统 - 数据库表结构设计 v2.0

> 生成时间：2026-09-17
> 版本：v2.0（依据《项目定案》修订）
> 数据库：PostgreSQL 16+，扩展 `pgvector`、`pg_trgm`
> 字符集：UTF8

---

## 1. 与 v1.0 的差异摘要

| 维度 | v1.0（MySQL + Milvus） | v2.0（PostgreSQL + pgvector） |
|---|---|---|
| 数据库 | MySQL 8.0 | **PostgreSQL 16+** |
| 向量存储 | Milvus 独立 Collection | **`chunks.embedding vector`，与元数据同表** |
| 隔离键 | `user_id` | **`tenant_id`** |
| 分层 | 用户 → 文档 | **租户 → 知识库 → 数据集 → 文档 → 块** |
| 配置 | 无表 | **`kb_configs` + `config_versions`** |
| 版本绑定 | 无 | **`chunks.config_version_id`（硬约束一）** |
| 父子切片 | 无 | **`chunks.parent_chunk_id` + `section_path`（决策 4）** |
| 来源类型 | 无 | **`chunks.source_type`（决策 5、6）** |
| 召回追踪 | `messages.retrieved_chunks`（仅最终结果） | **`retrieval_traces` + `retrieval_trace_items`（硬约束二）** |
| 重嵌入任务 | 无 | **`tasks` 表 + `reembed_jobs` 表（硬约束三）** |
| 软删除 | `deleted_at` | 保留 |
| 主键 | BIGINT AUTO_INCREMENT | **BIGINT + IDENTITY / GENERATED** |
| 时间类型 | DATETIME | **TIMESTAMPTZ** |

### 5.3 `chunks`（块 + 向量）★ 核心表

**这是 v2.0 变化最大的表。向量与元数据同表，过滤条件可下推。**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK | |
| tenant_id | BIGINT | NOT NULL | **冗余隔离键，避免 join 才能过滤** |
| kb_id | BIGINT | NOT NULL | 冗余 |
| dataset_id | BIGINT | NOT NULL | 冗余 |
| document_id | BIGINT | NULL, FK→documents | 与 record_id 二选一 |
| record_id | BIGINT | NULL, FK→records | 与 document_id 二选一 |
| source_type | VARCHAR(10) | NOT NULL | **`doc` / `record`（决策 5、6）** |
| chunk_index | INT | NOT NULL | 文档/记录内顺序 |
| content | TEXT | NOT NULL | 原文 |
| embed_text | TEXT | NOT NULL | 实际送入嵌入模型的文本（含 section_path 前缀） |
| content_hash | VARCHAR(64) | NOT NULL | 去重 |
| token_count | INT | NOT NULL | |
| section_path | TEXT | NULL | **如「第三章 费用管理 > 3.2 报销标准」（决策 4）** |
| parent_chunk_id | BIGINT | NULL, FK→chunks | **为父子切分预留（决策 4），第一版为 NULL** |
| chunk_type | VARCHAR(20) | NOT NULL DEFAULT 'text' | text / list / table_placeholder |
| config_version_id | BIGINT | NOT NULL, FK→config_versions | **硬约束一：该向量的配置版本** |
| embedding_model | VARCHAR(200) | NOT NULL | 冗余，便于排查 |
| embedding_dim | INT | NOT NULL | 冗余，便于排查与校验 |
| embedding | vector | NULL | **pgvector 列，不声明维度（决策 7）** |
| metadata | JSONB | NULL | 页码、解析器信息等 |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

**约束：**
```sql
PRIMARY KEY (id)
CHECK ( (document_id IS NOT NULL) <> (record_id IS NOT NULL) )
CHECK ( source_type IN ('doc','record') )
```

**索引（关键）：**
```sql
-- 过滤下推用的复合索引（检索时必须带 tenant_id + kb_id + config_version_id）
INDEX idx_chunks_scope ON chunks (tenant_id, kb_id, dataset_id, config_version_id, source_type)
INDEX idx_chunks_doc   ON chunks (document_id)
INDEX idx_chunks_rec   ON chunks (record_id)
INDEX idx_chunks_parent ON chunks (parent_chunk_id)
INDEX idx_chunks_hash  ON chunks (kb_id, content_hash)
```

**向量索引（按维度与配置版本分别创建）：**

```sql
-- 必须在数据写入有一定量、且维度确定后创建；每个 config_version 的维度固定
-- 示例：为 config_version_id = 1、source_type = 'doc' 建立 HNSW 索引
CREATE INDEX idx_chunks_vec_v1_doc
ON chunks USING hnsw ((embedding::vector(1024)) vector_cosine_ops)
WHERE config_version_id = 1 AND source_type = 'doc';

-- 记录路单独一个索引（可分别调参）
CREATE INDEX idx_chunks_vec_v1_rec
ON chunks USING hnsw ((embedding::vector(1024)) vector_cosine_ops)
WHERE config_version_id = 1 AND source_type = 'record';
```

> **维度变更处理（决策 7 的落地方式）：** pgvector 要求同一索引内维度一致。因此「换维度」等价于「新建一批索引 + 全量重嵌入 + 切换 `active_config_version_id`」，不是就地修改。旧版本向量与索引在灰度期保留，验证后清理。

**检索 SQL 形态（示意）：**

```sql
SELECT id, content, section_path, 1 - (embedding <=> $1::vector) AS score
FROM chunks
WHERE tenant_id = $2
  AND kb_id = $3
  AND config_version_id = $4
  AND source_type = 'doc'
ORDER BY embedding <=> $1::vector
LIMIT $5;
```

租户、知识库、配置版本、来源类型四个过滤条件在同一条 SQL 内完成，这是 pgvector 相对独立向量库的核心收益。

### 10.2 分区策略

只对**增长快且需要按时间清理**的表分区，其余表不分区。

## 11. 表大小估算

前提：多租户，单租户约 5 万份文档，每篇平均 20 个 chunk，留存 1 年对话。

| 表 | 预估行数 | 预估大小 |
|---|---|---|
| tenants / users / kb_members | 千级 | < 5 MB |
| knowledge_bases / datasets | 百级 | < 1 MB |
| kb_configs / config_versions | 千级 | < 5 MB |
| documents | 50,000 | ~30 MB |
| records | 100,000 | ~200 MB |
| **chunks（含向量）** | **1,000,000** | **~6 GB**（1024 维 × 4B + 索引 ≈ 6 KB/行） |
| conversations | 200,000 | ~60 MB |
| messages | 2,000,000 | ~2 GB |
| **retrieval_traces / items** | **40,000,000** | **~40 GB**（保留 90 天后归档） |
| tasks | 500,000 | ~200 MB |
| audit_logs | 1,000,000 | ~500 MB |

**结论：向量占用约 6GB，追踪数据是最大的表（约 40GB），必须按期清理。** 7TB 硬盘完全不是瓶颈。

**若使用 2560 维（4B 模型）：** `chunks` 表向量部分约 13GB，HNSW 索引约 20GB，合计约 35GB，仍然可接受。

## 12. 注意事项

1. **`tenant_id` 强制注入**：数据访问层统一处理，不依赖调用方。这是多租户隔离的最后一道防线。
2. **软删除与唯一约束**：PostgreSQL 的部分唯一索引（`WHERE deleted_at IS NULL`）是必需的，否则软删除后无法重建同名资源。
3. **`chunks` 表冗余 tenant_id / kb_id / dataset_id**：目的是让检索的过滤条件全部落在同一张表上，避免 join 影响向量索引使用。写数据时由应用层保证一致性。
4. **向量索引的创建时机**：数据量小的时候创建 HNSW 索引收益不明显，且索引构建成本高。建议数据积累到一定规模后再创建，先靠顺序扫描验证正确性。
5. **不要在同一索引内混入不同维度的向量**：按 `config_version_id` + `source_type` 建立带 `WHERE` 条件的部分索引。
6. **追踪表先建**：先建 `retrieval_traces` 与 `retrieval_trace_items`，再写检索逻辑。顺序反了会导致追踪字段变成事后补丁。
7. **时间字段统一 TIMESTAMPTZ**，存储 UTC，展示层转换。
8. **外键约束**：核心表之间使用数据库外键（PostgreSQL 外键性能开销可接受）；`chunks` 与配置版本之间必须有外键，因为这关系到数据一致性。
9. **分页**：大表使用游标分页（基于 id），避免 OFFSET。
10. **`content_hash` 去重**：同一知识库内相同内容的 chunk 应复用已有向量（配置版本相同时），避免重复嵌入。
