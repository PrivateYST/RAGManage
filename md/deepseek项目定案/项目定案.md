# RAG 知识库系统 - 项目定案

> 定案时间：2026-09-17
> 定案方式：grilling 逐项收敛，15 项关键决策全部由项目方确认
> 文档性质：**决策基线**。与 `md/` 目录下的四份 v1.0 设计文档存在冲突，以本文档为准。

---

## 0. 一句话定性

**这不是知识库管理系统，是检索质量决定一切的系统。**

文档管理、权限、标签、文件夹树都只是外壳。真正的命门是切片策略、召回质量、重排与上下文拼装。管理界面做得再完整，检索不准，整个系统就没有价值。

## 2. 三条硬约束

以下三条不满足，则第 2、6 项决策全部失效。

### 约束一：`config_version` 必须落库

每条向量记录必须携带「这向量是哪一版配置算出来的」。

原因：配置全数据化 + 可重跑，意味着改配置后旧向量与新区量会并存。没有版本标记，检索结果无法解释，也无法回滚。

### 约束二：召回链路追踪必须第一版就有

每次问答必须存下：各路召回的 chunk id、各路分数、融合前后排名。

原因：这是多路召回（决策 6）的**必要条件**，不是可观测性的锦上添花。没有它，无法判断多路召回到底比单路好还是差。

实现要点：追踪表带时间字段，支持分区或定期清理。按每天数千次问答估算，一年是百万级记录，它会是库里最大的表。

### 约束三：重嵌入任务机制必须完整

必须具备：进度、断点续跑、灰度（新旧向量并存）、回滚。

原因：配置全数据化 + 文档份数多，重嵌入是**日常操作**而非一次性任务。

## 3. 当前环境的真实瓶颈

| 资源 | 现状 | 判断 |
|---|---|---|
| CPU | 2 × Xeon E5-2683 v4（2016 年，32 核 64 线程），2.10 GHz | **瓶颈**。结构感知解析吃 CPU，十万级文档是数天量级 |
| 内存 | 80GB DDR4 ECC（标称 2133，实际跑 1866） | 开发够用，大规模解析队列时会紧张 |
| GPU | RTX 4090 ×1，24GB（开发机）；10 卡 48G（未上架） | **瓶颈**。24G 上 27.3B 必须 4bit 量化；4B 嵌入/重排开发阶段跑不了 |
| 操作系统 | Windows 10 专业版 19045（开发机） | **真问题**。vLLM 等推理框架不支持 Windows，解析工具坑多 |
| 硬盘 | 800GB SSD + 8TB HDD（可用约 7TB） | 不是瓶颈。十万级 chunk × 2560 维 × 4 字节 ≈ 1GB |
| 网卡 | Intel I350 千兆 | 内部部署够用 |

**关键结论：存储不是问题，CPU 和显存才是。**

## 4. 与 md/ 现有文档的冲突清单

`md/` 目录下的四份文档（生成于 2026-09-16）与本次定案存在系统性冲突，需按下表同步修订。

| 维度 | md/ 现有设计 | 本定案 | 修订动作 |
|---|---|---|---|
| 向量库 | Milvus 2.4 + pymilvus | **pgvector** | 三份文档全部替换；删除 Milvus 相关 Collection 设计、etcd + MinIO 依赖、`uk_vector_id` 语义 |
| 关系库 | MySQL 8.0 + aiomysql | **PostgreSQL**（与 pgvector 同库） | 数据库、驱动、JSON 字段、分区语法全部改写；`mysqldump` → `pg_dump` |
| 切片策略 | `RecursiveCharacterTextSplitter`，chunk_size=512，overlap=50 | **结构感知切片** | 替换第 5 节 RAG 工具链；解析层从「提取纯文本」改为「提取带层级结构的文档树」 |
| 解析工具 | pdfplumber / python-docx / PaddleOCR | **docling / MinerU / unstructured**（版面 + 标题层级 + 表格） | 替换第 6 节；OCR 与服务层统一 |
| 嵌入模型 | bge-large-zh-v1.5（1024 维固定） | **Qwen3-Embedding 0.6B + 4B，维度配置驱动** | 替换第 4.2 节；删除写死的 `dim=1024` |
| 生成模型 | Qwen 2.5 7B Instruct | **本地 27.3B 模型** | 替换第 4.1 节及 vLLM 启动命令 |
| 重排 | 未提及 | **Qwen3-Reranker 0.6B + 4B** | 新增章节 |
| 检索方式 | 单路向量检索 + 可选混合检索 | **多路召回 + 融合（文档路/记录路）** | 重写第 2.3 节检索模块 |
| 向量表结构 | `document_chunks.vector_id` 映射 Milvus 主键 | **向量直接存在 pgvector 表中** | 重写 `document_chunks` 表；新增 `embedding vector`、`config_version`、`parent_chunk_id`、`section_path`、`source_type` |
| 多租户键 | `user_id`（每用户一个 Collection） | **`tenant_id`**（每租户过滤下推） | 所有表补 `tenant_id`；重写隔离逻辑 |
| 数据分层 | 无知识库/数据集层 | **知识库 → 数据集** | 新增两张表 |
| 配置 | 无配置表（参数硬编码在代码） | **配置全数据化 + 配置版本表** | 新增 `kb_configs`、`config_versions` |
| 追踪 | `messages.retrieved_chunks` JSON（只有最终结果） | **独立检索追踪表（各路明细）** | 新增 `retrieval_traces` / `retrieval_trace_items` |
| 任务队列 | Celery + Redis | 保留，但需补充**重嵌入任务**类型与断点续跑 | 修订任务表与任务分类 |
| 开发环境 | 假设 Ubuntu 22.04 | **WSL2（图一那台 4090 机器）** | 修订硬件/软件环境章节 |
| GPU 分配 | 7 卡 LLM + 3 卡 Embedding（基于已上架的 10 卡） | **当前仅 4090 24G 单卡**，10 卡未上架 | 按「开发 / 生产」两套环境分别写 |

**处理建议：不要直接改 md/ 里的旧文档**（会丢失历史对比），而是按本定案重新产出四份 v2.0 文档，旧文档保留归档。

## 5. 第一周执行清单

按顺序执行，不可跳步。

### Step 1：环境（图一那台机器）

1. 安装 WSL2（Ubuntu 22.04 LTS）
2. 在 WSL 内用 Docker 起 PostgreSQL + pgvector
3. **开发库与生产库分离命名**（如 `rag_dev` / `rag_prod`），配置文件区分

### Step 2：最小链路跑通（一份 Markdown）

1. 一份 Markdown 文档 → 结构感知解析（保留标题层级）
2. 按结构切片 → 写入 `section_path`
3. 调 Qwen3-Embedding 0.6B 生成向量 → 写入 pgvector
4. 查询 → 向量检索 → 调本地 27.3B 生成回答

### Step 3：追踪表先行

**先建追踪表，再写检索逻辑。顺序不能反。**

一旦检索逻辑先写完，追踪字段就是事后补丁；先建表，检索逻辑天然带追踪。

### Step 4（第二周）：配置与版本

1. 建 `kb_configs` 表（切片参数、模型名、检索参数）
2. 建 `config_versions` 表
3. 向量记录绑定 `config_version`
4. 重嵌入任务骨架（进度 + 断点续跑）

### 明确不碰

- 表格解析（决策 5，第二批）
- 多租户权限矩阵（第一版只做单租户功能，但表结构带 `tenant_id`）
- 可视化配置界面
- Mac Studio
- 10 卡机部署

## 6. 风险与已知取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| 复杂度前移 | 决策 2（全数据化）+ 决策 6（多路召回）是两个复杂度放大器，第一版工作量比最小可用 RAG 大三倍以上 | 这是明确选择的结果，不视为意外。若想先验证效果，可先花一天做「固定配置 + 单路召回」的验证版 |
| CPU 解析瓶颈 | E5-2683 v4 跑结构感知解析，十万级文档是数天量级 | 重嵌入/重解析任务必须支持断点续跑与进度可见 |
| 显存不足 | 4090 24G 上无法同时跑 27.3B + 4B 嵌入 | 开发阶段 27.3B 走 4bit 量化，嵌入只用 0.6B；4B 相关压测等 10 卡机 |
| 10 卡机不确定 | 型号、显存、是否独占、系统均未确认；且尚未上架 | 模型服务地址进配置，按「独占、充足算力」设计并留降级开关；部署前必须实地确认 |
| Windows 兼容性 | 推理框架与部分解析工具在 Windows 上支持差 | 服务层统一跑在 WSL2；不要走 Windows 原生 |
| 生产索引被误刷 | 配置可改可重跑 + 开发/生产同库 = 某个下午顺手把生产向量刷成实验版本，且因向量无语义标记可能数天后才发现 | 开发库与生产库物理分离（硬约束） |
| 生成模型幻觉 | 27.3B 稠密模型在「无答案时明确说不知道」这类指令遵循上不如小模型 | 生成模型名进配置（决策 10），必要时换小模型做严格问答模式 |

## 7. 待确认事项（不阻塞开工）

1. **10 卡机的准确信息**：型号、单卡显存、是否独占、操作系统、是否已上架。这是唯一需要离开文档去实地核实的事实。
2. 文档总量级：目前「份数很多，不确定」，需在第一批数据入库后给出实际数字（影响重嵌入任务的批次设计）。
3. 生成模型的准确名称与量化和精度方案。
