| 维度 | v1.0 | v2.0 |

## 2. 总体路线（重构后的五阶段）

```
阶段 0：链路验证（1-2 周）          ← 新增，v1.0 没有
    用固定配置 + 单路召回，验证检索到底行不行
        ↓ 通过才继续
阶段 1：数据内核（3-4 周）
    表结构 + 配置体系 + 结构感知解析切片 + 嵌入 + 追踪表
        ↓
阶段 2：检索内核（3-4 周）
    多路召回 + 融合 + 重排 + 生成 + 完整追踪
        ↓
阶段 3：管理面（3-4 周）
    认证 + 知识库/文档/数据集管理 + 配置界面 + 重嵌入任务界面
        ↓
阶段 4：结构化数据与打磨（2-3 周）
    D 类来源通道 + 性能优化 + 真实数据压测
        ↓
阶段 5：产品化能力（后置）
    连接器、评测面板、用量统计、开放 API
```

**总计约 3-4 个月（1-2 人）。** 与 v1.0 的 17 周接近，但顺序完全不同。

**为什么新增阶段 0（重要）：**

决策 2（配置全数据化）与决策 6（多路召回）是两个复杂度放大器，第一版工作量比「最小可用 RAG」大三倍以上。如果检索质量本身不成立（切片错了、模型不匹配、文档不适合做 RAG），多路召回和全数据化配置都是在优化一个不成立的东西。

**阶段 0 的成本是一到两周，收益是避免在错误方向上投入三个月。** 如果你的时间成本高于这个比例，跳过它。

## 3. 阶段 0：链路验证（1-2 周）

**目标：** 用最简单的方式回答一个问题——**这套东西检索得准吗？**

### 范围

- 一份到 20 份真实文档（Markdown 或 DOCX）
- 固定配置（切片参数写死在代码里，不做配置表）
- 单路向量检索（文档路），不做融合、不做重排
- 不做认证、不做界面（用脚本或 Swagger 调用）
- **但要做追踪表**（因为这是硬约束，早做晚做都要做，先做成本更低）

### 任务清单

- [ ] WSL2 装好，PostgreSQL + pgvector 起起来（决策 12）
- [ ] 建 `chunks`、`config_versions`（只有一条记录）、`retrieval_traces`、`retrieval_trace_items` 四张表
- [ ] 结构感知解析：先只支持 Markdown（最简单，标题层级显式存在）
- [ ] 结构感知切片：按标题层级切，记录 `section_path`
- [ ] 调 Qwen3-Embedding 0.6B 生成向量，写入 pgvector
- [ ] 向量检索 + 简单生成（Prompt 里带 `section_path`）
- [ ] **建 10-20 条真实问题作为验证集**，人工判断答对率

### 验收标准（决定是否继续）

- ✅ 用 10-20 条真实问题测试，**答对率达到 60% 以上**
- ✅ 答错时能通过追踪表判断是「没召回」还是「召回了但答错」
- ✅ 肉眼查看切片结果，`section_path` 正确，没有把语义单元切断

**不达标怎么办：**
- 如果「没召回」占多数 → 切片策略或嵌入模型有问题，先调这两个，不要进入阶段 1
- 如果「召回了但答错」占多数 → 生成模型的 Prompt 或上下文组织方式有问题，这是更容易修的问题
- 如果答对率极低且找不到原因 → 停下来，重新评估文档是否适合做 RAG

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **检索质量不达标** | 高 | 阶段 0 先行验证，不达标不进入阶段 1 |
| **CPU 解析瓶颈** | 高 | E5-2683 v4（2016 年）跑结构感知解析慢；重嵌入/重解析必须支持断点续跑；考虑解析任务独立队列限并发 |
| **显存不足（开发机）** | 中 | 4090 24G 上 27.3B 必须 4bit 量化；4B 嵌入与重排开发阶段跑不了，接口先写好 |
| **10 卡机信息不明** | 中 | 型号/显存/独占性/系统均未确认且未上架；所有模型地址进配置，按「独占」设计并留降级开关 |
| **Windows 兼容性** | 中 | 服务层统一在 WSL2；GPU 服务在 Windows 宿主机跑，通过 IP 通信 |
| **生产索引被误刷** | 高 | 开发库与生产库**物理分离**（硬约束），配置不共用 |
| **多路召回无收益** | 中 | 阶段 2 结束时有明确的数据结论；若无收益，回退到 `single_route` 模式（接口已支持） |
| **追踪表膨胀** | 中 | 按期分区 + 90 天清理，`trace_cleanup` 定时任务 |
| **生成模型幻觉** | 中 | Prompt 强制约束；模型名进配置，必要时切小模型做严格问答 |
| **团队规模假设** | 高 | 本路线按 1-2 人设计；若实际人力更多，可并行推进阶段 1 与阶段 3 |

## 13. 与 v1.0 计划的关键差别提醒

v1.0 的计划（16-17 周、5-8 人、先做基础设施再做功能）**不适用于当前情况**：

1. **团队规模不同**：v1.0 假设 5-8 人分工，本项目是 1-2 人。所有并行任务串行化后，周期需要重估。
2. **没有提前验证检索质量**：v1.0 把「向量检索优化」放在第 9 周，即在写完认证、文档管理、对话之后才验证检索。**这是最危险的排期**——如果检索不成立，前面 8 周全部作废。
3. **技术栈假设不同**：v1.0 基于 MySQL + Milvus，v2.0 是 PostgreSQL + pgvector，数据层和部署方式全部不同。
4. **缺少三条硬约束**：`config_version`、召回追踪、重嵌入机制，v1.0 完全没有。这三项不是可选项，是决策 2 与决策 6 的必然产物。

**v2.0 的核心排期原则：先验证检索成立，再建设备。**
