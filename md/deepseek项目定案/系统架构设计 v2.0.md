> 生成时间：2026-09-17
> 版本：v2.0（依据《项目定案》修订）
> 依据：`项目定案/项目定案.md` 15 项决策 + 3 条硬约束

## 1. 与 v1.0 的差异摘要

| 维度 | v1.0 | v2.0 |
|---|---|---|
| 向量存储 | Milvus（独立服务 + etcd + MinIO） | **pgvector（与关系库同库）** |
| 关系库 | MySQL 8.0 | **PostgreSQL 16+** |
| 数据分层 | 用户 → 文档 | **租户 → 知识库 → 数据集 → 文档** |
| 切片 | 固定窗口 512/50 | **结构感知切片** |
| 检索 | 单路向量检索 | **多路召回（文档路/记录路）+ 融合重排** |
| 配置 | 硬编码 | **全数据化 + 配置版本化** |
| 可观测 | 仅记录最终引用 | **全链路召回追踪（各路明细）** |
| 隔离键 | `user_id` | **`tenant_id`** |
| 环境 | Ubuntu 单机 | **开发（WSL2 + 4090）/ 生产（10 卡机）双环境** |
| 部署形态 | 单机全栈 | **GPU 服务与业务服务分离** |

```
│ 全部元数据    │   │              │   │ 解析/嵌入/重跑│   │              │
│ + 全部向量    │   │              │   │              │   │              │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

**关键结构变化说明：**

1. **向量与元数据同库。** 租户/知识库/数据集/权限过滤条件可以直接在一条 SQL 里与向量检索同时下推，不需要「先查向量库再回关系库过滤」的两步操作。这是选择 pgvector 的核心收益。
2. **没有独立向量数据库服务。** 不需要 etcd、不需要 MinIO（对象存储改为本地文件系统或独立部署的 MinIO，与向量无关）。
3. **AI 推理服务与业务服务分离。** 业务服务可以跑在 WSL2 里，GPU 服务跑在宿主机或独立机器，通过 OpenAI 兼容接口通信。

## 3. 核心模块设计

### 3.1 数据分层与租户隔离

```
tenant（租户）
  └── knowledge_base（知识库）        ← 配置锚点、权限锚点
        └── dataset（数据集）          ← 第一版界面不暴露，默认存在一个
              └── document（文档）     ← 来源类型：文件 / 结构化记录
                    └── chunk（块）    ← 切片产物，向量挂在这里
```

**隔离规则（硬要求）：**

- 所有业务表带 `tenant_id`，包括 `chunk` 表（冗余，避免 join 才能过滤）。
- **查询必须由数据访问层强制注入 `tenant_id` 条件**，不依赖调用方自觉。实现方式：统一 Repository 基类，所有查询构造器默认带 tenant 过滤，需要跨租户的场景必须显式调用特权方法。
- 第一版只实现单租户功能，但表结构与过滤逻辑从一开始就在。

### 3.2 配置体系（决策 2：全数据化）

配置分三层：

| 层级 | 存储位置 | 内容 | 变更频率 |
|---|---|---|---|
| 部署配置 | 环境变量 / `.env` | 数据库连接、Redis 地址、推理服务 endpoint、密钥 | 低 |
| 知识库配置 | `kb_configs` 表 | 切片参数、嵌入模型名、向量维度、检索 top-k、各路权重、融合参数、重排模型名、生成模型名 | **高（界面可改）** |
| 配置版本 | `config_versions` 表 | 每次生效的配置快照 + 哈希 | 每次变更生成一版 |

**重跑机制（配置变更的必然结果）：**

```
配置变更 → 生成新 config_version
         → 计算受影响范围（哪些 chunk 的向量需重算）
         → 创建重嵌入任务（可断点续跑）
         → 新向量写入，标记新 config_version
         → 灰度期：新旧向量并存，检索可按版本过滤
         → 验证通过后清理旧向量 / 失败则回滚
```

**向量维度策略（决策 7）：**

- pgvector 的向量列**不声明维度**（`embedding vector`），维度由索引和数据约束在应用层保证。
- 因为不同维度的向量不能共存于同一索引，实际实现为：**按「知识库 × 配置版本」建立独立的部分索引或独立表分区**，索引维度跟随该配置。
- 换嵌入模型 = 新建一套索引 + 全量重嵌入 + 切换，不是就地修改。

### 3.3 解析与切片（决策 4：结构感知）

**v1.0 的做法**：提取纯文本 → 按字符数切 → 丢失所有结构。
**v2.0 的做法**：提取文档结构树 → 按语义单元切 → 保留层级路径。

```
原始文档
   ↓ 解析层（docling / MinerU / unstructured）
结构化文档树
   {
     sections: [
       { level: 1, title: "第三章 费用管理", path: "第三章 费用管理",
         blocks: [ {type: "paragraph", text: "..."},
                   {type: "table", ...},          ← 第二批处理
                   {type: "list", items: [...]} ] }
     ]
   }
   ↓ 切片层
chunk 列表（每个 chunk 携带）：
   - content：原文
   - section_path："第三章 费用管理 > 3.2 报销标准"
   - chunk_index：在文档内的顺序
   - parent_chunk_id：NULL（为父子切分预留，决策 4）
   - token_count
   - content_hash（去重）
```

**切分规则：**

1. 最小语义单元为切点：段落、列表项组、条款。
2. 相邻小段可合并，直到接近目标 token 数（目标值进配置），但**不跨 section 边界合并**。
3. 超长单元（如整节）做二次切分，切点优先选句子边界，二次切分的块 `section_path` 保持一致。
4. 每个 chunk 在最终嵌入文本前拼接 `section_path` 作为前缀，让向量携带上下文归属信息。

**第一版范围（决策 5）：** 只做电子版文档（Markdown / Word / 电子版 PDF / 网页）+ 结构化数据（D）。**表格（C）放第二批**，遇到表格时按普通文本处理并记录告警。

### 3.4 检索链路（决策 6 + 11：多路召回 + 融合 + 重排）

```
用户问题
   ↓
[可选] 查询改写
   ↓
┌──────────────────────┬──────────────────────┐
│  文档路召回           │  记录路召回            │
│  source_type='doc'   │  source_type='record' │
│  pgvector 向量检索    │  pgvector 向量检索     │
│  top_k_doc (配置)    │  top_k_rec (配置)     │
└──────────┬───────────┴───────────┬──────────┘
           │                       │
           └───────────┬───────────┘
                       ↓
              融合（RRF 或加权，参数进配置）
                       ↓
              重排（Qwen3-Reranker）
                       ↓
              取 top_n 组装上下文
                       ↓
              生成（本地 27.3B）
                       ↓
          ★ 全链路追踪落库（各路 chunk id、分数、融合前后排名）
```

**多路召回的三种可选模式（接口需支持切换，第一版实现第一种即可）：**

- `fuse_then_rerank`：先融合所有路的候选，再统一重排
- `rerank_then_fuse`：各路先独立重排，再融合
- `single_route`：只用文档路（用于对照实验与降级）

**追踪表是硬约束（约束二）：** 每次问答必须在 `retrieval_traces` + `retrieval_trace_items` 落库，记录各路召回的 chunk id、各路分数、融合前后排名。**先建追踪表，再写检索逻辑。**

### 3.5 生成层（决策 10）

- 生成模型名进配置，可改。
- 调用协议统一为 OpenAI 兼容接口，本地 vLLM/Ollama 与远程 API 均可，服务地址进配置。
- 配置结构支持**按场景指定模型**（如「严格问答」用指令遵循更强的小模型，「开放总结」用 27.3B），第一版只用一个场景。
- Prompt 模板中强制包含「仅依据给定上下文回答，无相关信息时明确说明不知道」。

### 3.6 异步任务（含重嵌入）

| 任务类型 | 触发 | 特点 |
|---|---|---|
| `document_parse` | 上传文档 | 吃 CPU，结构感知解析慢 |
| `document_embed` | 解析完成 | 吃 GPU（嵌入服务） |
| `reembed` | 配置变更 / 手动触发 | **可断点续跑、可灰度、可回滚** |
| `record_sync` | 结构化数据源同步 | 增量 upsert |
| `trace_cleanup` | 定时 | 清理/归档过期追踪记录 |

**重嵌入任务必须支持：** 进度上报、按 chunk 范围分片、中断后续跑、新旧版本并存、一键回滚。

## 4. 部署架构（双环境）

### 4.1 开发环境（当前可用）

```
WSL2（Ubuntu 22.04 LTS）跑在 Windows 10 主机上
┌──────────────────────────────────────────────┐
│  Nginx                                        │
│  FastAPI                                      │
│  PostgreSQL 16 + pgvector（开发库 rag_dev）   │
│  Redis                                        │
│  Celery Worker ×2（解析任务为主）              │
└──────────────────────────────────────────────┘
宿主机（Windows）：
  - RTX 4090 24GB
  - 生成模型：27.3B，4bit 量化（约 15-17GB 显存）
  - 嵌入模型：Qwen3-Embedding **0.6B**（4B 跑不了，显存不够）
  - 重排模型：Qwen3-Reranker **0.6B**
```

**开发环境限制：** 4B 嵌入与 4B 重排无法在开发阶段跑；相关接口与配置要写好，压测等生产环境。

### 4.2 生产环境（10 卡机，待上架）

```
Linux 服务器
┌────────────────────────────────────────────┐
│  业务服务：Nginx / FastAPI / Celery / Redis │
│  数据：PostgreSQL 16 + pgvector（生产库）    │
├────────────────────────────────────────────┤
│  AI 推理服务（GPU 宿主机直跑，非容器）       │
│  - 生成模型：27.3B（可全精度）              │
│  - 嵌入：Qwen3-Embedding 4B ×N（TEI/vLLM）  │
│  - 嵌入：Qwen3-Embedding 0.6B（批量重嵌入） │
│  - 重排：Qwen3-Reranker 4B                  │
└────────────────────────────────────────────┘
```

**待确认（不阻塞开工）：** 10 卡机的型号、单卡显存、是否独占、操作系统。

**降级开关：** 所有模型服务地址进配置。若 10 卡机实为共享资源池，只需把 endpoint 换成远程地址，不改代码；但需补充排队与抢占续跑逻辑。

### 4.3 环境分离（硬约束）

- **开发库与生产库物理分离**（不同实例或至少不同 database），配置不共用，向量不共用。
- 理由：配置全数据化 + 可重跑意味着「改配置 → 重嵌入 → 覆盖向量」是顺手操作；同库会导致生产索引被实验版本无声覆盖，且因向量无语义标记，可能数天后才发现。

## 6. 可观测性

### 6.1 召回追踪（硬约束二）

必须记录并可通过 API 查询：

- 各路召回的候选 chunk id 与分数
- 融合参数与融合后排名
- 重排前后排名变化
- 最终进入上下文的是哪些
- 全链路耗时分解（召回 / 融合 / 重排 / 生成）

用途：判断多路召回是否优于单路；定位「答错」是召回错了还是生成错了。

### 6.2 系统监控

- 系统级：CPU / 内存 / 磁盘 / GPU 利用率与显存
- 应用级：API 请求量、响应时间、错误率、Celery 队列深度
- 业务级：知识库数、文档数、chunk 数、问答量、重嵌入任务积压

**重点监控项：** Celery 队列深度（解析是 CPU 瓶颈，容易积压）、嵌入服务响应时间、重嵌入任务进度。

### 6.3 日志

结构化日志（JSON），关键路径（检索、生成、重嵌入）带 `trace_id` / `config_version` 便于串联。

## 7. 安全

- 全站 HTTPS，CORS 白名单，API 限流。
- 密钥与部署配置走环境变量，**不进代码库**。
- `tenant_id` 过滤由数据访问层强制注入，不依赖上层传参。
- 文件上传做类型与大小校验，存储路径与文件名解耦，防止路径穿越。
- 权限模型（第一版）：租户内角色 = 管理员 / 编辑者 / 只读，作用域到知识库。

---

## 8. 性能设计要点

| 环节 | 优化手段 |
|---|---|
| 向量检索 | HNSW 索引；过滤条件下推（同一条 SQL 完成 tenant + 数据集 + 权限过滤）；按知识库/版本分索引 |
| 解析 | 解析任务独立队列，限并发（CPU 瓶颈）；结果落库可复用，不重复解析 |
| 嵌入 | 批量请求；重嵌入任务分片并支持夜间调度 |
| 检索缓存 | 同一 (知识库, 配置版本, 问题) 的结果缓存，配置变更即失效 |
| 生成 | 并发信号量限制；流式输出 |
| 追踪数据 | 定期归档/清理，避免成为最大表 |

## 9. 扩展性

- **水平扩展：** FastAPI 与 Celery Worker 无状态，可多实例；数据库读写分离后置。
- **向量规模扩展：** 若突破千万级且 pgvector 力不从心，再将检索层抽象为可替换接口（预留，不提前实现）。
- **多模态扩展（第二批）：** 表格结构识别、OCR、图片理解。
- **产品化能力（第二步）：** 数据源连接器、可视化流水线配置、检索效果评测面板、用量统计、开放 API。内核已按此设计（配置数据化、流水线可重放、全链路可观测）。

## 10. 总结

v2.0 的核心变化是**三件事**：

1. **存储收敛**：向量与元数据同库（pgvector），用复杂度换来了过滤下推和多路召回的实现便利。
2. **检索升级**：结构感知切片 + 多路召回 + 融合重排 + 全链路追踪，这是「检索质量优先」的直接体现。
3. **配置数据化**：配置进库、版本化、可重跑、可回滚，这是第二步产品化能力的地基。

架构的复杂度集中在前两件事上，这是决策 2 与决策 6 的必然代价，属于明确选择的结果。
