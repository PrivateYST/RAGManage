## 1. 与 v1.0 的选型差异

| 类别 | v1.0 | v2.0 | 变更原因 |
|---|---|---|---|
| 关系数据库 | MySQL 8.0 | **PostgreSQL 16+** | 与 pgvector 同库（决策 9） |
| 向量数据库 | Milvus 2.4 + etcd + MinIO | **pgvector** | 决策 9：过滤下推、架构收敛 |
| 向量库 SDK | pymilvus | psycopg / asyncpg | 同上 |
| 嵌入模型 | bge-large-zh-v1.5（1024 维固定） | **Qwen3-Embedding 0.6B + 4B** | 决策 8：中文强、双档、维度可变 |
| 嵌入推理 | TEI（3 副本） | TEI 或 vLLM（按规模） | 保持 |
| 重排 | 无 | **Qwen3-Reranker 0.6B + 4B** | 决策 11：多路召回必须配重排 |
| 生成模型 | Qwen 2.5 7B Instruct | **本地 27.3B 模型** | 决策 10 |
| 切片 | `RecursiveCharacterTextSplitter` | **结构感知切片（自研）** | 决策 4 |
| 文档解析 | pdfplumber / python-docx | **docling / MinerU / unstructured** | 决策 4：需要结构树，不是纯文本 |
| 多租户键 | user_id | **tenant_id** | 决策 3 |
| 编排 | 无 | **保留 Celery**，新增重嵌入任务类型 | 决策 2 的必然结果 |
| 开发环境 | Ubuntu 22.04 | **WSL2（Windows 10 开发机）** | 决策 12 |
| 对象存储 | MinIO | **本地文件系统起步**，规模上来再上 MinIO | 向量已入库，对象存储只放原始文件 |

## 4. 数据存储

### 4.1 PostgreSQL + pgvector（决策 9）

| 项 | 选型 |
|---|---|
| 数据库 | PostgreSQL 16+ |
| 向量扩展 | pgvector 0.7+ |
| 其他扩展 | pg_trgm（模糊搜索，可选） |
| 驱动 | asyncpg（异步） |
| 向量索引 | HNSW（`vector_cosine_ops`） |
| 迁移 | Alembic |

**关键配置（`postgresql.conf`）：**

```ini
shared_buffers = 4GB                    # 约内存的 25%
effective_cache_size = 24GB
maintenance_work_mem = 2GB              # HNSW 索引构建需要较大内存
work_mem = 64MB
max_parallel_maintenance_workers = 4    # 加速索引构建
max_connections = 200
```

**HNSW 索引参数建议：**

```sql
CREATE INDEX idx_chunks_vec_hNSW
ON chunks USING hnsw ((embedding::vector(1024)) vector_cosine_ops)
WITH (m = 16, ef_construction = 64)
WHERE config_version_id = 1 AND source_type = 'doc';

-- 查询时设置搜索宽度（会话级）
SET hnsw.ef_search = 100;
```

| 参数 | 说明 | 取值建议 |
|---|---|---|
| `m` | 每层最大连接数 | 16（默认，够用） |
| `ef_construction` | 构建时搜索宽度 | 64（构建快）；追求召回率可到 128-256 |
| `hnsw.ef_search` | 查询时搜索宽度 | 40-100，越高召回越好但越慢 |

**为什么不选 Milvus（决策 9 的权衡记录）：**

| 维度 | pgvector | Milvus |
|---|---|---|
| 元数据过滤 | **同库同 SQL，条件下推** | 元数据需重复存，过滤逻辑分散 |
| 事务一致性 | **天然一致** | 需自行处理跨系统同步 |
| 备份 | **pg_dump 一次搞定** | 独立备份流程 |
| 架构复杂度 | **低（一个服务）** | 高（Milvus + etcd + MinIO） |
| 千万级以上性能 | 较弱 | **强** |
| 维度灵活性 | 部分索引支持不同维度 | 集合维度固定 |

**判断：在当前规模（十万级 chunk）下 pgvector 完胜；若未来突破千万级，检索层已抽象为可替换接口，届时再评估。**

### 4.2 Redis

用途不变：缓存、Celery Broker/Backend、任务进度、限流计数。

**新增用途：** 检索结果缓存，key 必须包含 `config_version_id`（配置变更即失效）。

```
retrieval:{tenant_id}:{kb_id}:{config_version_id}:{query_hash}
```

### 4.3 对象存储

| 阶段 | 方案 |
|---|---|
| 第一版 | **本地文件系统**（`/data/rag/files/`，按 tenant/kb 分目录） |
| 规模上来 | MinIO（S3 兼容） |

**理由：** 向量已入 pgvector，对象存储只放原始文件，第一版用本地文件系统可减少一个服务依赖。迁移成本低（存储路径字段已抽象）。

## 5. AI 模型层

### 5.1 嵌入模型（决策 8）

| 用途 | 模型 | 维度 | 部署阶段 |
|---|---|---|---|
| 开发迭代 / 批量重嵌入 | **Qwen3-Embedding-0.6B** | 1024 | 开发 + 生产 |
| 生产检索 | **Qwen3-Embedding-4B** | 2560 | 仅生产（10 卡机） |

**关键特性：** Qwen3-Embedding 系列支持 MRL（自定义输出维度），不同尺寸模型维度不同。**维度由配置驱动（决策 7），不写死。**

**部署方式：**

```bash
# 0.6B（开发机 4090 上可跑）
text-embeddings-router \
  --model-id Qwen/Qwen3-Embedding-0.6B \
  --port 8001 \
  --max-client-batch-size 32 \
  --max-batch-tokens 16384

# 4B（仅生产环境，每卡一实例 + Nginx 负载均衡）
CUDA_VISIBLE_DEVICES=2 text-embeddings-router \
  --model-id Qwen/Qwen3-Embedding-4B \
  --port 8011 \
  --max-batch-tokens 32768
```

**双档策略（决策 8 的落地）：**

- 调切片策略、调检索参数的阶段，用 0.6B 做重嵌入试验（快）
- 配置稳定后，切 4B 做一次全量重嵌入（慢但质量高）
- 这正是「配置版本 + 灰度 + 回滚」机制的用途

### 5.2 重排模型（决策 11）

| 模型 | 用途 | 部署 |
|---|---|---|
| **Qwen3-Reranker-0.6B** | 开发迭代 | 开发 + 生产 |
| **Qwen3-Reranker-4B** | 生产 | 仅生产 |

**为什么必须做重排：** 多路召回后，文档路与记录路的分数尺度不同，不可直接比较。重排模型提供统一尺度的相关性评分，是融合排序的最后一道闸门。不做重排的多路召回归根结底是在猜参数。

**代价：** 只对融合后的 top-50 做重排，不是全库，成本可接受。

### 5.3 生成模型（决策 10）

| 项 | 说明 |
|---|---|
| 当前模型 | 本地部署的 27.3B 模型 |
| 调用协议 | OpenAI 兼容接口 |
| 地址来源 | **配置（`kb_configs.generation`）**，不写死在代码 |
| 场景化 | 配置结构支持按场景指定模型（`strict_qa` / `summary`），第一版只启用一个场景 |

**vLLM 启动（生产，全精度）：**

```bash
python -m vllm.entrypoints.openai.api_server \
  --model <本地模型路径> \
  --served-model-name qwen-local-27b \
  --host 0.0.0.0 --port 8000 \
  --tensor-parallel-size 2 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.90
```

**开发（4090 24G，4bit 量化）：**

```bash
# Ollama 或 vLLM + AWQ/GPTQ 量化
ollama serve
ollama pull <量化版本>
# 约占用 15-17GB 显存，剩余显存不足以再跑 4B 嵌入模型
```

**已知限制：** 27.3B 稠密模型在「无答案时明确说不知道」这类指令遵循上，不如小的指令微调模型。因此 Prompt 中必须强制约束，且必要时可切换小模型做严格问答模式（这正是生成模型名进配置的理由）。

### 5.4 GPU 资源规划

**开发环境（当前可用）：**

| 资源 | 分配 |
|---|---|
| RTX 4090 24GB | 生成模型（4bit 量化，~16GB）+ 嵌入 0.6B（~2GB）+ 重排 0.6B（~2GB），几乎占满 |
| CPU（E5-2683 v4） | 解析任务，**瓶颈所在** |
| 内存 80GB | 够用 |

**生产环境（10 卡机，待上架）：**

| GPU | 用途 |
|---|---|
| 0-1 | 生成模型 27.3B（Tensor Parallel） |
| 2-5 | 嵌入 Qwen3-Embedding-4B ×4 副本（Nginx 负载均衡） |
| 6 | 嵌入 Qwen3-Embedding-0.6B（批量重嵌入专用，避免抢占在线服务） |
| 7-8 | 重排 Qwen3-Reranker-4B ×2 副本 |
| 9 | 备用 / 重嵌入临时扩容 |

**关键设计：重嵌入用独立的 GPU 实例，不抢占在线服务。** 否则每次改配置都会导致问答服务变慢。

## 6. 文档解析与切片

### 6.1 解析工具选型（决策 4）

| 工具 | 强项 | 用途 |
|---|---|---|
| **docling**（IBM 开源） | 版面分析、标题层级、表格、多格式 | **主力**：PDF / DOCX / PPTX |
| **MinerU** | 中文 PDF、公式、表格 | 中文 PDF 备选 |
| **unstructured** | 格式覆盖最广 | 兜底 |
| markdown 原生解析 | — | Markdown 直接按标题层级构建树 |

**为什么不沿用 pdfplumber / python-docx：** 它们只能提取纯文本，**拿不到标题层级和段落结构**，而结构感知切片（决策 4）的前提正是这些结构信息。

### 6.2 结构感知切片（自研，决策 4）

不引入 LangChain 的 TextSplitter，因为它是按字符切分，与本决策相反。

**自研模块：`app/rag/chunking/structure_aware.py`**

```python
def chunk_document(doc_tree: DocTree, config: ChunkingConfig) -> list[Chunk]:
    """
    规则：
    1. 以最小语义单元为切点（段落、列表组、条款）
    2. 相邻小单元可合并至接近 target_tokens，但不跨 section 边界
    3. 超长单元二次切分，优先句子边界
    4. 每块记录 section_path
    5. embed_text = section_path 前缀 + content
    """
```

**产出字段对应表结构：** `content`、`embed_text`、`section_path`、`chunk_index`、`parent_chunk_id`（第一版为 NULL）、`token_count`、`content_hash`、`chunk_type`。

**第一版范围（决策 5）：** 电子文档（Markdown / DOCX / 电子版 PDF / HTML）+ 结构化数据（D）。**表格（C）放第二批**，遇表格时按文本处理并在 `documents.metadata` 记录告警。

### 6.3 结构化数据通道（D 类）

不走解析层，走独立同步通道：

```
数据源（数据库 / API / 导出文件）
   ↓ 字段映射与文本拼装（模板进配置）
content 文本
   ↓ 长度判断
   ├── 短记录 → 一个 chunk
   └── 长记录 → 按字段分组切多个 chunk
   ↓ 嵌入
写入 chunks（source_type = 'record'）
```

同步策略：按 `external_id` + `content_hash` 做增量 upsert，内容未变则跳过嵌入。

- GPU 服务：宿主机直跑，不容器化（vLLM + TEI）
- **数据库物理分离**：`rag_prod` 独立实例（决策 13）

**降级开关：** 所有模型服务地址进配置。若 10 卡机实为共享资源池，改 endpoint 即可，但需补充排队与抢占续跑逻辑。

## 10. 性能目标（重新校准）

| 指标 | 目标 | 说明 |

| 文档上传 | < 2 秒 | 仅上传，解析异步 |

## 13. 选型决策记录（为什么是这些）

| 决策 | 选择 | 核心理由 |
|---|---|---|
| 向量库 | pgvector | 过滤条件同 SQL 下推；事务一致；备份统一；架构收敛。代价是千万级性能较弱，当前到不了 |
| 关系库 | PostgreSQL | pgvector 的宿主，非独立选择 |
| 嵌入模型 | Qwen3-Embedding 0.6B/4B | 中文强；双档满足「快速迭代」与「生产质量」两种需求；同族 Reranker 配套 |
| 重排 | Qwen3-Reranker | 决策 6（多路召回）的必要配套，不是可选优化 |
| 切片 | 自研结构感知 | 现成库都是按字符切，与本决策相反 |
| 解析 | docling | 唯一能同时给出标题层级与版面结构的成熟开源方案 |
| 消息队列 | 保留 Celery | 已有积累，重嵌入任务需要可靠的断点续跑 |
| 对象存储 | 第一版本地文件系统 | 向量已入库，少一个服务依赖 |
